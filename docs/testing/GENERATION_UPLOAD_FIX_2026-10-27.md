# 生成超时修复（2026-10-27）

## 原因

失败发生在上传阶段，尚未进入图片融合。编辑器去背景后导出 PNG，原上传准备仅压缩大尺寸 JPEG，因此透明 PNG 会直接转成 Base64，再通过 `/studio/jobs` 上传。

线上 Nginx 记录显示，两次失败分别在 13:56:43、14:01:52 结束：`request_s≈125.18`，`status=400`，`upstream_s=-`，约收到 1.5 MB 后客户端提前断开。对应请求没有进入 API。此前 13:33:37 的成功提交总耗时 42.178 秒，API 处理仅 0.745 秒，主要时间也花在入口接收请求。截图中的 Canvas readback 与 worker 提示不是本次失败原因。

## 修改

- 生成前把静态输入限制到最长边 1024 像素，与现有队列服务归一化尺寸一致。
- 不透明图片上传 JPEG；透明图片上传 JPEG 颜色和单独的无损灰度 PNG 透明度图。服务器还原为 RGBA 后，继续走原来的贴图、融合、GIF、排队和重新编辑流程。用户编辑原图不被替换。
- `image_masks` 是可选且与 `images` 对齐的字段。旧版单张图片数据继续可用；持久化任务仍保存统一 PNG，不保存新的传输结构。
- 还原检查编码、数量、图片格式、尺寸和动画帧数，最多同时处理两次。直接生成缓存包含透明度数据，避免同色不同透明度图片命中同一结果。
- 上传超时显示图片上传提示；保留提交的幂等键，重试可找回已经接收的任务。
- 不增加模型、GPU 或运行时依赖。

## 验证

- 165 项后端测试和 35 项前端测试通过，微信构建及包体检查通过。
- 微信开发者工具实际原生 Canvas：1024×1024、2,084,944 字节透明测试图，上传 JSON 223,702 字节（旧 Base64 约 2.78 MB），准备耗时 105 ms。颜色文件 81,609 字节，透明度文件 86,141 字节。
- 将原生编码结果在后端还原，1,048,576 个透明度字节全部一致，尺寸保持 1024×1024。
- 在启用域名校验的微信开发者工具中，通过首页实际生成按钮验证公网 HTTPS、登录队列、worker 融合和结果下载，两次完成分别为 8.952 秒、15.083 秒；游客直接生成分别为 8.512 秒、10.620 秒。时间随网络情况变化，不代表真机延迟保证。
- 下载结果包含 14 个实际变化的 GIF 帧，总时长 1400 ms。
- 公网请求体限速 16 KiB/s 后生成成功，总耗时 21.199 秒，其中融合处理 870.1 ms。
- 原生流程中刻意丢弃服务器已接收的提交响应，再次点击生成后成功收图：两次请求使用同一幂等键，服务器返回同一任务，未重复创建。
- 测试图片为私有历史验证素材构造的同尺寸透明输入，不是截图中照片的原始文件；测试图、凭据及成品不入库。
