# 根据测试结果安排修改

本清单按公开上线的风险排序。这里的建议没有被当作已经部署的修复。

## P0：公开上线前必须解决

1. **完成目标主机安全验收。**维护者需要确认主机来源、系统补丁、访问权限、凭据、隔离与恢复方案。若存在历史安全事件，必须先按私下交接流程恢复可信状态，不能用应用测试通过替代。
2. **处理不可信图片解析依赖。**当前 `^10.0.0` 约束阻止升级到多个上游安全公告的修复版本。应在隔离环境升级到当前适配且已修复的版本、限制允许的图片格式、重新跑全部模板和编辑测试，再部署。不要只改版本号而不复测。

## P1：公开开放和扩量前解决

3. **限制持久素材与磁盘。**视频最多 60 MiB、每分钟四次、保留七天，缺少账号累计字节和全局磁盘水位限制；手动私有模板也没有总量上限或完整删除入口。建议先实现可配置的账号存储预算、上传每日字节预算、全局目录上限、低磁盘拒绝和孤立素材回收。分钟限速不能代替存储预算。
4. **隔离共用服务。**主页、OpenClaw 与应用应分别以低权限身份运行并设置上限；部署示例中 API 和 worker 各最多两核，合计可占满四核机器。将具有代理执行能力的服务放到独立低权限环境，给应用设置共同资源预算，保留系统及其他服务余量。不要未经测试直接调大 worker 并发。
5. **补齐用户数据控制。**实现注销、账号数据删除、私有模板删除、撤回发布、反馈／偏好清除、投诉和下架。删除时覆盖数据库、原图、处理缓存、预览、回放与备份保留规则。
6. **完成隐私与正向发布验收。**真实 wx.login、隐私授权、微信内容检查通过、保存与分享还需要真机和真实开发者权限。现有 mock 证明拒绝／失败路径，不代表微信平台已批准上线。
7. **设置流量和成本告警。**总预算 1500 GB 是三个业务共用额度。应以云控制台账单和实际账期为准，建立 50%／70%／85%／95% 分级告警，接近上限时限制新上传和新任务，保留领取已有作品的通道。这里是建议，未创建定时任务或修改云配置。

## P2：优先改善的功能体验

8. **修正七个模板的必填说明。**alipay、always_like、ask、google_captcha、make_friend、wechat_pay、why_have_hands 按声明最少输入会失败，补名字后可生成。应统一模板契约和前端校验：需要名字时明确提示、未填写时阻止提交，或采用用户明确确认的默认名字。
9. **增加统一的微信导出适配。**全模板样例中 GIF 最大约 3.84 MB，而视频导出有 500 KiB 限制。应保留原版下载，同时提供适合微信入口的压缩版本，逐一真机验证。不要将“生成成功”等同于“可以添加为微信表情”。
10. **改进 AI 识图制模的成功反馈。**真实 OCR 清晰样例得到约 0.896 的置信度，低于 0.95 门槛，正确进入手动处理，但没能交付可编辑模板。需要更丰富样本、中文／英文字体对比、置信度校准、手动校正文案和重建效果检查。不能只降低阈值后自动公开。
11. **重新设计识图失败后的额度。**当前 `needs_manual` 仍占用当天的 AI 模板机会。建议失败退回额度，同时加独立的短时尝试限制，防止反复识图挤占 CPU。
12. **解释压缩取舍，增加短片段选项。**本轮两个 9 秒结果都是 45 帧，平均约 5 fps；保留时长但可能不够流畅。可增加“更流畅／更清晰”等明确选项，优先引导用户取 3～6 秒，最终效果必须真机观看。
13. **优化公网等待。**分类接口源站约 31 ms，而开发机经公网的三个样本约 5.18～7.74 s。优先检查网络路径、Tunnel、首屏请求并行、缓存和等待提示；不能仅据此增加 CPU。中国移动网络和不同运营商需要另测。

## P3：后续完善

- 依赖锁定、分平台测试矩阵和升级流程；处理 npm 构建工具及 pip 管理工具命中的公告，区分运行路径与开发路径。
- 更多人物、动物、遮挡、逆光、复杂背景的带标注效果数据集。
- OCR、采集与内容检查的长期成功率、失败原因和重试观测。
- 私有下载频率、异常流量、磁盘增长、队列年龄、失败率和耗时监控。
- 隔离预发布环境的长时间稳定性、容量和完整灾难恢复演练。

关闭问题需要提交实现、对应测试和新的验收证据。当前的交付状态应表述为“源码和开发验收资料可交接，公开上线有阻断项”。
