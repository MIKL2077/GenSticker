# 部署、资源、流量、备份与回滚

适用对象：维护者。这里描述部署示例和建议，不会自动修改线上服务。

## 部署示例

小程序通过 HTTPS 访问网关，网关转发到仅监听回环地址的 API。API 写入持久队列，独立 worker 处理推荐、模板和视频。以下以可能同时承载主页和代理服务的共用主机作规划示例，不公开现网审计状态。

- 机器：4 vCPU、16 GB RAM，整机每月 1500 GB 流量额度。
- API 与 worker：各最多两核、2 GiB 内存，账号为 gensticker。
- 两个 CPU 限额相加已是四核，不能把它当作给其他业务留了两核。
- 状态目录含账户库、功能库、私有素材与结果；模型与缓存另外存放。
- 配置示例见 `deploy/`。已有脚本针对当前服务器路径，迁移前逐行核对，不能在新机器直接盲跑。

实际主机状态通过私下交接，不在公开仓库发布现网审计快照。性能样本见 [报告](testing/REPORT_2026-10-20.md)。

## 上线资源建议

先完成主机安全验收与隔离，再决定配额：

1. 让 API、worker 属于同一应用 slice，初始共同 CPU 预算建议约两核，给主页、OpenClaw 和系统保留余量；先在预发布环境测响应后再确定最终值。
2. worker 仍先保持一个独立进程，模型／渲染线程有界。增加进程会复制模型内存，并改变 SQLite 与队列行为。
3. 按服务设置内存、进程数、重启策略与日志轮转。主页、OpenClaw 也需要低权限运行和自己的上限。
4. 监控可用内存、CPU 节流、磁盘水位、队列年龄、失败率和 P95，不能只看健康接口是否为 200。
5. 写入前做全局磁盘保护；每账号配额、孤立文件和过期任务必须一并清理。

建议低于 10 GiB 空闲磁盘时拒绝新素材并告警；最后的阈值应结合系统盘、日志、备份和实际增长验证。不要删除仍被活动任务、私有模板或公共模板引用的文件。

## 1500 GB 流量预算

这是三个业务共享的总额度。用户截图显示的是套餐额度及取整后的使用率，不能据此获得精确剩余字节或账期起止。最终以云控制台的当前账期、计费方向和账单为准。

可以先人为划分：GenSticker 900 GB、其他业务 300 GB、余量 300 GB。**这是规划示例，不是当前实际使用占比。**按十进制 1 GB=1,000,000,000 字节计算。

本轮两批九图的完整结果响应分别约 0.463 MB 和 2.178 MB；这没有包含缩略图、重复下载、页面资源、请求头和代理开销。两段视频成品约 0.313 MB 和 0.378 MB，也没有包含视频上传和用户再次领取的全部开销。

保守规划可先假设：每批九图共消耗 3 MB 响应流量，每个视频流程 1 MB，每次模板浏览平均 0.03 MB。实际参数应由上线日志和云账单校准。

```text
每日业务流量(MB) = 每日九图批次 × 3 + 每日视频次数 × 1 + 每日浏览次数 × 0.03
月度业务流量(GB) = 每日业务流量(MB) × 账期天数 ÷ 1000
```

例：每天 1000 人，每人两批九图、半次视频、十次浏览，按 30 天估算约 204 GB/月。这个例子只说明流量算法，**不能据此承诺这台机器支持 1000 日活或每秒多少请求**；CPU、排队、瞬时峰值和下载重试另算。

上传字节也应记录，供应商是否计入套餐须核对具体规则。OpenClaw 的模型调用、文件传输、Tailscale 与其他业务出站，不会出现在小程序 API 的响应体统计中。Nginx 日志还缺少加密与隧道开销，而且有轮转缺口，不能直接拿来对账。

建议在云账期用量到 50%、70%、85%、95% 时逐级告警，先减少采集和新上传，再限制新生成；保留登录、健康检查及已有成品领取。不要在临近上限时继续无上限自动重试。当前只提供建议，未创建定时监控或更改云配置。

## 部署顺序

1. 核对提交、依赖与模型哈希，确认安全阻断项已解除。
2. 先在隔离环境安装依赖、中文字体、FFmpeg；验证真实模型与全部模板。
3. 配置独立服务账号、私有目录、后端环境文件及数据库权限。
4. 以回环地址启动 API，再启动 worker；确认私有任务能实际完成。
5. 验证 Nginx 限流、请求体大小、代理超时及受信代理地址；不要关闭微信域名校验。
6. 备份当前代码、配置、数据库及私有文件，再灰度切换。
7. 验证主页和 OpenClaw 仍可用，观察资源、错误和队列。
8. 最后构建微信 production 包，配置平台合法域名和隐私用途，完成真机测试再提交审核。

## 备份与恢复

备份至少包含：账号库、功能库、私有原图／预览／结果／回放、模板素材、模型清单、配置、服务单元和 Nginx 配置。密钥单独加密保存，备份目录不对外提供静态服务。

SQLite 使用 WAL 时不要只在服务运行中复制一个 `.sqlite3` 文件。使用 SQLite 在线 backup API，或在受控停机窗口同时保存数据库及关联状态。两个数据库与图片的跨文件一致性还需要完整恢复流程。

数据库备份副本的单独检查应使用私有临时目录，检查完清理测试副本。**尚未证明整套业务可以在全新机器上恢复**。上线前应在隔离环境恢复完整备份，检查用户归属、图片可读、队列和模型，再记录恢复时间与允许的数据损失窗口。

建议明确 RPO（最多可接受多久的数据损失）和 RTO（多久内恢复服务），例如“每日备份”只有在恢复验证通过后才有意义。备份不要只保存在运行应用的同一台机器上。

## 回滚

前端保留上一个可用微信版本；后端保留上一个源码及依赖环境，配置随发布版本归档。数据库结构变化必须先评估兼容性，不可直接用旧程序覆盖新库。

回滚时先暂停新任务进入，让已接受任务在可控状态下完成或保留；切回代码／环境／配置，再验证健康、账户、私有结果与主页。需要恢复数据库时同步处理关联文件，并说明会丢失哪些时间段的新数据。

不要为了测试回滚而在共享生产机直接停主页、OpenClaw 或 worker。本轮没有执行生产重启、完整回滚或故障注入。
